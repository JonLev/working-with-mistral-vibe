# Repo maintenance

How this repo's quality gates, generators, and version system work, and how
to run them. Adapted from the source repo's docs/workflows pattern:
every rule here is enforced by a script, and the doc + script pair is the
unit of maintenance.

## Run the gates locally

Every gate is a standalone script under `scripts/gates/`; there is exactly
one implementation and two entry points (pre-commit and CI):

| Gate | Script | What it enforces |
|---|---|---|
| Link | `scripts/gates/check-links.sh` | Every relative markdown link and image in every `.md` file resolves to an existing file. Mermaid `click ... href` targets inside fenced diagram blocks are held to a stricter rule: the target file must exist AND any anchor must resolve to a real heading of that file (zero-tolerance). No external-URL checking in v1. |
| Naming policy | `scripts/gates/check-claude-terms.sh` | `claude`, `anthropic`, `settings.json`, `hooks.json` appear nowhere in `guide/`, `examples/`, `quiz/`, `machine-readable/`, `docs/` outside `docs/workflows/claude-term-allowlist.txt`. |
| Frontmatter | `scripts/gates/check-frontmatter.sh` | Every `guide/**/*.md` page has `title`, `description`, `tags` frontmatter and exactly one "Verified against ... Documented surface ..." banner. |
| Markdown lint | `scripts/gates/check-markdown.sh` | markdownlint-cli2 with the minimal documented config in `.markdownlint-cli2.jsonc`. |

Direct invocation:

```bash
bash scripts/gates/all.sh        # all four gates
bash scripts/gates/check-links.sh
```

Or install pre-commit once (`pip install pre-commit && pre-commit install`);
`.pre-commit-config.yaml` runs the same scripts plus the drift checks on
every commit. CI runs the identical set.

### The selftest

`bash scripts/gates/selftest.sh` proves the gates catch what they claim to:
it copies the repo to a temp dir, plants each fixture from
`scripts/fixtures/` (a broken link, a planted claude term, a page missing
its frontmatter and banner), and requires the matching gate to fail. It also
requires the clean copy to pass. CI runs it on every push.

## Generated artifacts

| Artifact | Generator | Source |
|---|---|---|
| `llms.txt`, `llms-full.txt` | `scripts/generate-llms.py` | `guide/` frontmatter + `VERSION` |
| `machine-readable/reference.yaml` | `scripts/generate-reference.py` | same frontmatter + ATX headings |
| `guide/vibe-guide.md` | `scripts/generate-monolith.py` | `scripts/monolith.yaml` (chapter spec) + each page's frontmatter description and TL;DR first sentence — the spine is delegation-only and cannot drift from the pages |

Properties (by construction, and checked in CI):

- One source, generated outputs — never edit `llms.txt`, `llms-full.txt`,
  or `machine-readable/reference.yaml` by hand. This is the deliberate fix
  for the source repo's hand-maintained llms.txt triple.
- Deterministic: no timestamps; page order is sorted by path.
- Idempotent: run twice, byte-identical output.
- Drift-checked: `--check` regenerates in memory and diffs against the
  committed files, failing on drift. Run it via pre-commit or:

```bash
python3 scripts/generate-llms.py --check
python3 scripts/generate-reference.py --check
```

## Versions

`VERSION` is the single source of truth. Every version-bearing artifact is
generated, so the sync is a regeneration, not a regex rewrite (simplified
from the source repo's VERSION chain):

| Artifact | Version marker |
|---|---|
| `llms.txt` | `Guide version X.Y.Z` |
| `llms-full.txt` | `Guide version X.Y.Z` |
| `machine-readable/reference.yaml` | `version: "X.Y.Z"` |
| `guide/vibe-guide.md` | `Guide version X.Y.Z` (regenerated by `scripts/generate-monolith.py`) |

Bump procedure:

```bash
# 1. Decide the new version and write it:
echo "0.2.0" > VERSION
# 2. Regenerate every version-bearing artifact and re-check:
scripts/sync-version.sh
# 3. Commit VERSION plus the regenerated files together.
```

`scripts/sync-version.sh --check` (pre-commit, CI) fails if any artifact
does not carry the current `VERSION`. A pre-release suffix
(`X.Y.Z-dev`, used by `scripts/release.sh --dry-run` and in-flight
releases) is accepted and propagates verbatim into the generated markers.

## What CI checks

`.github/workflows/ci.yml` runs on every push to `main` and on pull
requests: the four gates (`scripts/gates/all.sh`), the generator drift
checks (llms.txt pair, reference.yaml, the monolith spine), the MCP
server content-sync check and its test suite, the quiz
validator (`scripts/validate-quiz.py`), the version-sync check, and the
gate selftest. There is nothing in CI that cannot be run locally with the
same scripts.

## The naming-policy gate and its allowlist

The style guide's naming policy (risk R1) bans the source product's terms
from the published content. The gate scans the content directories and
honors `docs/workflows/claude-term-allowlist.txt` — one path per line, every
entry justified inline. The only sanctioned content home for these terms is
the "Migrating from Claude Code" chapter (guide/surfaces/), listed
in the allowlist with its justification.

Current non-migration entries exist because the terms are *the subject*:
the style guide quotes them as the rule itself, and the mechanics oracle in
`docs/mechanics/` maps the source product's concepts to Vibe equivalents
by design. Shrinking this list is a standing goal; growing it
needs a written justification in the file.

## Documented decisions and limits

- Markdown lint scope excludes `docs/mechanics/` (the oracle is a frozen
  verification transcript — findings there cannot be fixed without
  redoing the verification) and
  `scripts/fixtures/` (deliberately malformed self-test inputs). Rationale
  comments live in `.markdownlint-cli2.jsonc`. A subtree override in
  `guide/diagrams/.markdownlint-cli2.jsonc` allows exactly the
  `<details>`/`<summary>` inline HTML of the dual Mermaid+ASCII format and
  nothing else.
- The link gate checks file existence for prose links, but for Mermaid
  `click` hrefs it also validates heading anchors; external URLs are not
  checked (v1; see the script header).
- The Python tooling (`scripts/lib/`) is stdlib-only by design — no virtual
  environment, no pip installs, works in CI and on any maintainer machine.
- `quiz/questions/*.yaml` carries the regenerated question bank; the
  placeholder file is gone. Every question is
  schema-validated with resolving `doc_reference` backlinks.
- The monolith spine `guide/vibe-guide.md` is delegation-only by
  construction: `scripts/generate-monolith.py` never copies page prose, so
  a paragraph that exists in a deep-dive page cannot exist in the spine.

## Release and CLI-release tracking

Two scripts and two pages extend this system from "the repo is consistent"
to "the repo stays current":

| Piece | What it does | Doc |
|---|---|---|
| `scripts/release.sh` | Mechanical half of a guide release: bump `VERSION`, regenerate, run the gates, print the changelog evidence. Never pushes, never publishes; the changelog entry is drafted by the maintainer from the actual diffs (the source repo's "do NOT auto-generate from diff" rule) | [release.md](release.md) |
| `scripts/check-vibe-release.sh` | Compares the guide's recorded documented surface (the oracle banner) against the latest public release (PyPI + repo tags) and the installed CLI; exits non-zero when a re-verification pass is due | [re-verification.md](re-verification.md) |
| `guide/releases.md` | The tracking page: a dated row per CLI release that affects the guide — what changed, whether the oracle was re-verified, when banners were re-stamped | the page itself |
| `CHANGELOG.md` | Per-release narrative entries, Keep-a-Changelog format, drafted from actual changes | [release.md](release.md) |

`check-vibe-release.sh` is wired into CI as a **warning**
(`continue-on-error: true`), deliberately: content staleness is not a build
failure, and a network flake must not turn the gate set red. It fails open
when it cannot reach PyPI or the repository — a green run during an outage
proves nothing; re-run it before trusting it.

## Dogfooding: the repo's own config

The guide teaches minimal, hand-written instruction files and repo-local
skills — so this repo uses exactly that:

- [`AGENTS.md`](../../AGENTS.md): the repo's own instruction file —
  commands, the mechanics-discipline and naming rules, the
  never-hand-edit list, and the no-push/no-publish rule. Minimal by design.
- `.vibe/skills/guide-maintenance/SKILL.md`: a repo-local skill (discovered
  via Vibe's `.vibe/skills/` search order) that encodes this maintenance
  workflow — run the gates, regenerate on drift, run the release check,
  follow the re-verification or release walkthrough. A maintainer (or an
  agent session) invokes it in-session instead of memorizing this page.
- [`CONTRIBUTING.md`](../../CONTRIBUTING.md): the proposal contract for
  external contributors — the gates to run first, the oracle-citation
  rule, the honesty rules, the translation policy pointer, the review
  path.

The launch surfaces themselves (README, the launch checklist, the prepared
org migration) are documented in
[launch-checklist.md](launch-checklist.md) and
[org-migration.md](org-migration.md).
